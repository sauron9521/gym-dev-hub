# Shared Agent Memory security primitives (Issue #39)

**Rollout status: separate opt-in operator token management, verified-only reads and proposal-only memory intake.** By default all memory GET routes return **503**; only verified list, detail or revisions `GET /v1/memory*` may return 200 after a third explicit `DEV_HUB_MEMORY_READ_HTTP_ENABLE=true` flag, verified local Bearer and separate Hub DB identity check. `GET /v1/memory/:id?repository=owner/name` and `GET /v1/memory/:id/revisions?repository=owner/name` use the same bearer+DB authorization; `/status` remains **503** regardless of credentials. The shared process-local `MemoryAuthorizationService` supplies tokens to the list gateway; `MemoryQueryService` is called only after per-request scoped DB authentication. No Codex agent, GitHub token, worktree grant, SSH key, localhost caller, iframe or MCP app receives new read or write access by default. Existing `agent-workspace.json`, Web and Codex continue working with the previous local-only behavior. See [memory read design](memory-read-api.md) and [ADR](architecture/shared-agent-memory.md).

## Separate opt-in configuration

Every value below must be configured _privately_ inside gitignored `apps/api/.env` **only when actively testing this control plane**. Do not copy secrets into prompts, PRs, logs, screenshots or repo files. Memory+security flags and the dedicated Hub memory database enable **only** operator credential management. A separate third flag below is required to enable the verified-memory **list, detail and bounded revision history**; an independent proposal flag enables `PROPOSED` inserts; separate local operator-only flags enable two-step `PROPOSED → VERIFIED` approval, `PROPOSED → REVOKED` rejection, or **first-generation** `VERIFIED → REVOKED` withdrawal; a fourth independent local operator flag allows two-step same-owner `VERIFIED → SUPERSEDED` with an already-verified replacement. All use different one-use grants and CAS. No MCP.

```dotenv
DEV_HUB_MEMORY_ENABLE=true
DEV_HUB_MEMORY_SECURITY_ENABLE=true
DEV_HUB_MEMORY_OPERATOR_SECRET=<NEW-INDEPENDENT-RANDOM-SECRET-AT-LEAST-32-BYTES>
DEV_HUB_MEMORY_ALLOWED_REPOSITORIES=sauron9521/gym-dev-hub
DEV_HUB_MEMORY_TRUSTED_ORIGIN=http://127.0.0.1:3100
DEV_HUB_MEMORY_EXTERNAL_READ_ENABLE=false
DEV_HUB_MEMORY_READ_HTTP_ENABLE=false
DEV_HUB_MEMORY_PROPOSALS_HTTP_ENABLE=false
DEV_HUB_MEMORY_APPROVAL_HTTP_ENABLE=false
DEV_HUB_MEMORY_REJECTION_HTTP_ENABLE=false
DEV_HUB_MEMORY_VERIFIED_REVOCATION_HTTP_ENABLE=false
DEV_HUB_MEMORY_SUPERSEDE_HTTP_ENABLE=false
```

Generate the operator secret locally with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`. Never reuse the worktree creation, task execution, Docker or GitHub token. `DEV_HUB_MEMORY_ALLOWED_REPOSITORIES` is a separate, exact `owner/name` list (maximum 16); **`GITHUB_REPOSITORIES` is not an authorization policy** and does not automatically grant rights. Only a literal `true` on both memory enable flags activates the _in-process primitives_. Invalid or missing secrets, invalid allowlist or non-loopback UI origin fails closed.

The memory control plane is **not ready for network exposure**. Both Next/Web and API must remain on loopback. A reverse proxy, SSH tunnel, Docker port publish, LAN address or CORS header is never authentication. Browser mutations require an exact trusted local `Origin` and allowed `Sec-Fetch-Site`; remote peer addresses, spoofed Host, cross-site origins and tokens placed in URL/query parameters fail closed. Future HTTP integration must still verify Bearer plus authenticated principal for each operation and prevent caching of secret-bearing responses. No cookie session is accepted here, so there is no implicit cookie-based CSRF authority.

## Operator-only HTTP credential lifecycle (Issue #39 follow-up)

These two **local-only** endpoints are registered, but **return 503 by default** until the independent memory+security flags, operator secret, exact repository allowlist, trusted local origin and dedicated Hub memory database are correctly configured and migrated:

| Route                                                  | Request                                                                                                                                                                                                                    | Successful result                                                              |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `POST /v1/memory/operator/credentials`                 | `Content-Type: application/json`, exact trusted `Origin`, `x-dev-hub-memory-operator-secret`, body `{ "kind":"agent", "repository":"owner/name", "agentId":"UUID", "taskId":"UUID", "sessionId":"UUID", "ttlSeconds":60 }` | HTTP 201: `credentialId`, one-time `bearerToken`, `expiresAt`, `READ_VERIFIED` |
| `DELETE /v1/memory/operator/credentials/:credentialId` | Exact trusted `Origin`, operator-secret header, generated credential UUID                                                                                                                                                  | HTTP 200: `{ "revoked": true/false }`                                          |

The operator secret is **not** an agent bearer, and neither secret is accepted as a URL/query, cookie, browser storage field or chat payload. Never place it in terminal command arguments or shell history, and never log raw request or response headers/bodies. Use a trusted local client capable of supplying the secret privately. The server requires a direct loopback TCP peer, a loopback `Host`, matching `Origin` on mutations, allowed `Sec-Fetch-Site`, JSON-only POST and a separate operator-secret header. `X-Forwarded-For` cannot grant local status. Responses disable caching and referers. Invalid/missing operator secret is 401 (bounded attempts), unsafe host/origin or scope 403, exhausted rate limit 429, missing/failed configuration or DB 503.

Only **session-bound agent** credential issuance is offered through HTTP. The operator may explicitly request a separate `permission: PROPOSE_MEMORY` credential when the independent proposal flag is enabled. Read-only credentials never gain proposal rights automatically. All agent credentials require an exact UUID tuple `repository + agentId + taskId + sessionId`; missing task or session is **403 before database access**. Internal agent bearer minting also refuses partial tuples. External/MCP credentials remain unmounted and are explicitly rejected by every local HTTP memory read endpoint even when `DEV_HUB_MEMORY_EXTERNAL_READ_ENABLE=true`. Before token issuance, the DB membership guard confirms the repository exists, all IDs belong to that repository, a session matches the task/agent pair, and a task-bound agent belongs to a real session. No token is minted if DB membership is absent or the DB cannot be checked. The raw bearer is returned once, stored as a hash in this Nest process only, revocable by ID and invalidated on restart or memory security flag/secret rotation. A separately gated **operator-only** `POST /v1/memory/operator/approval-grants` reviews DB-sourced untrusted content and issues a one-use grant for `POST /v1/memory/:id/approve`, which performs CAS with immutable revision and durable metadata-only audit. No persistent credential database table is introduced. All verified-only list/detail/revision reads require the same explicit read flag and authenticated DB-bound bearer; status remains 503. The agent's **only** write route is separately opted-in `POST /v1/memory/proposals`, which records untrusted `PROPOSED` entries with transactional audit and idempotency. A second, independent local-operator-only workflow can promote a precisely reviewed record to `VERIFIED` using one-use grant + CAS; see [proposal intake](memory-proposals.md) and [operator approval](memory-approval.md).

## Identity & capabilities

| Identity                   | Credential                                                                                                      | Allowed operations                                                                                                                                                                                 | Lifetime / revocation                                                                                             |
| -------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `operator`                 | Independent 32–256 byte secret, compared via constant-time SHA-256 digest                                       | Provision explicit read-only **or separately flagged proposal-only** credentials; issue/revoke fixed-purpose one-use _approval grants_                                                             | Never sent to agent prompt or stored in DB. Changing/invalidating configuration clears all credentials and grants |
| `agent`                    | One 32-byte random bearer issued only after explicit operator authentication, hashed in process memory          | Exactly one permission: `READ_VERIFIED` **or** `PROPOSE_MEMORY` (only unverified append); no approve/existing-record update/shell/Git/merge/Docker                                                 | Maximum 15 minutes; revoke by credential ID; restart invalidates                                                  |
| `external` MCP client      | Separate, explicitly provisioned random bearer; `DEV_HUB_MEMORY_EXTERNAL_READ_ENABLE=true` required in addition | `READ_VERIFIED` only; never operator approval, never remote network access granted by token alone                                                                                                  | Maximum 5 minutes; revocable; no external HTTP/MCP endpoint yet                                                   |
| One-time operator approval | Fresh 32-byte random grant token bound to `repository + action + recordId + expectedRevision + fingerprint`     | Separately flagged `PROPOSED → VERIFIED`, `PROPOSED → REVOKED`, or `VERIFIED → REVOKED` or an already-approved same-owner `VERIFIED → SUPERSEDED` pair by **different actions**; no general editor | 45 seconds, single use, grant-ID revocation, wrong-context attempt consumes token, restart/rotation revokes       |

Credential and grant maps contain **only SHA-256 token hashes**, never raw bearer values. A token is shown once as the direct result of an explicit trusted operator action; it must not be logged or sent to Codex. Audit snapshots are bounded to 256 metadata-only events: type, fixed operator actor ID, allowed repository, generated resource ID and timestamp, never secret, token, arbitrary chat body, Git SHA from an unverified source or raw prompts. No file-based token store; restarting Nest revokes everything. Bad operator-secret attempts are limited to 12 per minute **per local process**; an eventual multi-instance auth deployment will require distributed rate limits and persistent revocation before the feature can be enabled remotely.

Before an operator can issue a read-only agent credential over HTTP, `MemoryOperatorCredentialService` now checks the explicitly allowed repository, validates all requested UUID scopes, and performs a read-only PostgreSQL membership check using the dedicated Hub memory database. An unknown repository, agent, task, session or unrelated agent/task pairing is refused **before** token creation. A valid session-bound agent bearer requires independent database binding **on every list, detail and revision request**; issuing a token alone does not activate reads. No browser localStorage/cookie, MCP interface or agent prompt has access to the operator secret. A read-token cannot create proposals or approve any grant. A separately provisioned `PROPOSE_MEMORY` token cannot read records, approve, revoke, supersede or access shell/Git; it only submits `PROPOSED` entries when the independent flag is enabled.

## Error boundaries and review gates

`memory-http-identity.ts` provides the strict HTTP bearer helper used by all opt-in memory read endpoints which accepts only a strict `Authorization: Bearer <43-character-token>` header after local network/Origin/Host checks and translates errors to **401** (missing/invalid credentials), **403** (forbidden scope or origin), **429** (rate limit), **503** (disabled/unavailable). No errors include raw secrets. Without the additional read flag all memory GET routes stay 503; status stays 503 unconditionally. The helper does not grant authority merely because the process is bound to `127.0.0.1`.

Security acceptance tests in `apps/api/test/memory-authorization.spec.ts` and `memory-http-identity.spec.ts` cover mandatory task/session binding, external-to-local-HTTP segregation, secret separation, default deny, explicit allowlist, remote/CSRF/Origin/Host rejection, token-URL rejection, anonymous read, per-repo/task scope, external-client opt-in, wrong operator secret, expired/replayed/revoked grants, secret rotation, rate limits and audit confidentiality. `pnpm check` exercises these with **no PostgreSQL connection**. The proposal slice introduces a dedicated, guarded Prisma migration for immutable idempotency and durable metadata-only audit; credential storage remains process-local and no new CLI commands are introduced.

**Next gate:** review completed memory read identity acceptance criteria and threat-model checks, then advance to human-approved proposals/mutation in Issue #40. List, detail and verified revisions have real positive and negative Nest HTTP e2e tests, strict query validation and independent opt-in. Issue #40 now also contains separately flagged operator-reviewed `PROPOSED → VERIFIED` CAS with source-bound grant and durable metadata audit. Issuing a grant alone does **not** verify knowledge: only a successful second explicit approval request may transition state. The separate rejection workflow now handles `PROPOSED → REVOKED`; first-generation verified-record revocation and strictly same-owner verified supersession are separately available, but per-human attribution, external source trust and full security acceptance remain open. Rollback is setting `DEV_HUB_MEMORY_PROPOSALS_HTTP_ENABLE=false` (which invalidates active tokens), or deploying the previous API release. An already applied migration is additive and retains append-only audit/proposal rows; do not drop those tables for routine rollback.

## Issue #39 security audit: session-bound agent HTTP (post-#95)

- **Operator secret and local boundary:** only the explicit separate memory operator secret can issue or revoke agent credentials; the socket peer, Host, trusted Origin and Fetch-Site are checked independently of forwarded headers. Anonymous/remote/CSRF and operator-token-as-agent requests cannot authorize memory writes (all agent writes remain separately gated and proposed-only; only the separate operator workflow may approve).
- **Minimum read identity:** all agent credentials now require an exact `repository + agentId + taskId + sessionId` combination. The operator credential body and in-process minting primitive reject partial agent tuples before any DB access; `verifyMemoryPrincipalBinding` revalidates this tuple and checks the exact same-repo task/session/agent relationship on **each** HTTP read. Agent ID alone cannot grant project-wide memory access. Existing tokens lacking the complete tuple are not accepted.
- **External/MCP separation:** enabling `DEV_HUB_MEMORY_EXTERNAL_READ_ENABLE` allows an independent **internal** external-token primitive, but never grants it access to the existing local agent HTTP routes, even with a valid token and loopback host. No MCP endpoint has been mounted.
- **Approval capabilities:** operator approval grants are 45-second, one-use, revocable, intent-bound primitives only. An independent local operator-only approval grant route and one-time CAS `PROPOSED → VERIFIED` route now exist. A separate [operator rejection route](memory-rejection.md) now provides `PROPOSED → REVOKED` via a **distinct** action-specific one-use grant, independently default-off. A further [verified-record revocation route](memory-verified-revocation.md) is independently default-off, requires revision 2 and preserves immutable history. A further [operator supersede workflow](memory-supersede.md) is independently default-off and requires two already verified same-owner records, one-to-one linkage and a distinct one-use grant. No general record editor exists; see [approval](memory-approval.md).
- **Audit and confidentiality:** credential/grant events contain only bounded IDs, an internal `local-operator` actor label and timestamps; never raw tokens, operator secrets, prompt text or DB connection details. The proposal path now persists agent identity, action and a SHA-256 digest in a separate immutable DB audit transaction. The operator approval slice persists before/after SHA-256 digests with its unique grant and `local-operator` actor label, guarded by CAS and a row lock. `REJECT_MEMORY_PROPOSAL` is now a separately gated immutable audit transition, never readable as verified memory. The separately gated `REVOKE_MEMORY_RECORD` action adds durable source-linked revision 3 and metadata-only before/after audit for initially verified records. A [separate supersede action](memory-supersede.md) now appends an immutable third revision and metadata audit while linking only two existing verified same-owner records. **Per-human identity**, external source trust and comprehensive adversarial acceptance remain outstanding in #40.
- **Security regression gates:** unit tests, real Nest HTTP request tests, and isolated real-PostgreSQL membership tests must deny missing/expired/revoked credentials, missing or foreign session/task identities, hostile Origin/Host, mixed agent/external authority and DB outages; normal Workspace/Codex flows and health must continue unaffected.

**Remaining acceptance before closing #39:** review a real operator approval route only together with #40's transaction, replay-safe grant consumption and persistent audited actor identity. The approval migration now enforces immutable repository/scope/task/session/agent ownership, kind, text and source SHA across revisions to prevent historical scope leaks. The separate operator approval flag enables only `PROPOSED → VERIFIED`, while proposal-only agent tokens cannot approve. Per-human identity and further state transitions remain separate acceptance gates. Keep the Hub API bound to loopback; do not publish it behind a reverse proxy.
