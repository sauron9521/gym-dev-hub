# Shared Agent Memory security primitives (Issue #39)

**Rollout status: opt-in operator token management and independent verified-memory list/detail/revision reads only.** By default all memory GET routes return **503**; only verified list, detail or revisions `GET /v1/memory*` may return 200 after a third explicit `DEV_HUB_MEMORY_READ_HTTP_ENABLE=true` flag, verified local Bearer and separate Hub DB identity check. `GET /v1/memory/:id?repository=owner/name` and `GET /v1/memory/:id/revisions?repository=owner/name` use the same bearer+DB authorization; `/status` remains **503** regardless of credentials. The shared process-local `MemoryAuthorizationService` supplies tokens to the list gateway; `MemoryQueryService` is called only after per-request scoped DB authentication. No Codex agent, GitHub token, worktree grant, SSH key, localhost caller, iframe or MCP app receives new read or write access by default. Existing `agent-workspace.json`, Web and Codex continue working with the previous local-only behavior. See [memory read design](memory-read-api.md) and [ADR](architecture/shared-agent-memory.md).

## Separate opt-in configuration

Every value below must be configured _privately_ inside gitignored `apps/api/.env` **only when actively testing this control plane**. Do not copy secrets into prompts, PRs, logs, screenshots or repo files. Memory+security flags and the dedicated Hub memory database enable **only** operator credential management. A separate third flag below is required to enable the verified-memory **list, detail and bounded revision history**; no flags enable record writes, MCP or agent mutations.

```dotenv
DEV_HUB_MEMORY_ENABLE=true
DEV_HUB_MEMORY_SECURITY_ENABLE=true
DEV_HUB_MEMORY_OPERATOR_SECRET=<NEW-INDEPENDENT-RANDOM-SECRET-AT-LEAST-32-BYTES>
DEV_HUB_MEMORY_ALLOWED_REPOSITORIES=sauron9521/gym-dev-hub
DEV_HUB_MEMORY_TRUSTED_ORIGIN=http://127.0.0.1:3100
DEV_HUB_MEMORY_EXTERNAL_READ_ENABLE=false
DEV_HUB_MEMORY_READ_HTTP_ENABLE=false
```

Generate the operator secret locally with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`. Never reuse the worktree creation, task execution, Docker or GitHub token. `DEV_HUB_MEMORY_ALLOWED_REPOSITORIES` is a separate, exact `owner/name` list (maximum 16); **`GITHUB_REPOSITORIES` is not an authorization policy** and does not automatically grant rights. Only a literal `true` on both memory enable flags activates the _in-process primitives_. Invalid or missing secrets, invalid allowlist or non-loopback UI origin fails closed.

The memory control plane is **not ready for network exposure**. Both Next/Web and API must remain on loopback. A reverse proxy, SSH tunnel, Docker port publish, LAN address or CORS header is never authentication. Browser mutations require an exact trusted local `Origin` and allowed `Sec-Fetch-Site`; remote peer addresses, spoofed Host, cross-site origins and tokens placed in URL/query parameters fail closed. Future HTTP integration must still verify Bearer plus authenticated principal for each operation and prevent caching of secret-bearing responses. No cookie session is accepted here, so there is no implicit cookie-based CSRF authority.

## Operator-only HTTP credential lifecycle (Issue #39 follow-up)

These two **local-only** endpoints are registered, but **return 503 by default** until the independent memory+security flags, operator secret, exact repository allowlist, trusted local origin and dedicated Hub memory database are correctly configured and migrated:

| Route                                                  | Request                                                                                                                                                                                                                                          | Successful result                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| `POST /v1/memory/operator/credentials`                 | `Content-Type: application/json`, exact trusted `Origin`, `x-dev-hub-memory-operator-secret`, body `{ "kind":"agent", "repository":"owner/name", "agentId":"UUID", "taskId":"UUID (optional)", "sessionId":"UUID (optional)", "ttlSeconds":60 }` | HTTP 201: `credentialId`, one-time `bearerToken`, `expiresAt`, `READ_VERIFIED` |
| `DELETE /v1/memory/operator/credentials/:credentialId` | Exact trusted `Origin`, operator-secret header, generated credential UUID                                                                                                                                                                        | HTTP 200: `{ "revoked": true/false }`                                          |

The operator secret is **not** an agent bearer, and neither secret is accepted as a URL/query, cookie, browser storage field or chat payload. Never place it in terminal command arguments or shell history, and never log raw request or response headers/bodies. Use a trusted local client capable of supplying the secret privately. The server requires a direct loopback TCP peer, a loopback `Host`, matching `Origin` on mutations, allowed `Sec-Fetch-Site`, JSON-only POST and a separate operator-secret header. `X-Forwarded-For` cannot grant local status. Responses disable caching and referers. Invalid/missing operator secret is 401 (bounded attempts), unsafe host/origin or scope 403, exhausted rate limit 429, missing/failed configuration or DB 503.

Only **agent** credential issuance is offered through HTTP; external/MCP credentials remain unmounted even when `DEV_HUB_MEMORY_EXTERNAL_READ_ENABLE=true`. Before token issuance, the DB membership guard confirms the repository exists, all IDs belong to that repository, a session matches the task/agent pair, and a task-bound agent belongs to a real session. No token is minted if DB membership is absent or the DB cannot be checked. The raw bearer is returned once, stored as a hash in this Nest process only, revocable by ID and invalidated on restart or memory security flag/secret rotation. There is **no HTTP approval grant route**, record mutation or credential database table. All verified-only list/detail/revision reads require the same explicit read flag and authenticated DB-bound bearer; status remains 503. No memory write routes exist.

## Identity & capabilities

| Identity                   | Credential                                                                                                      | Allowed operations                                                                                                       | Lifetime / revocation                                                                                             |
| -------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `operator`                 | Independent 32–256 byte secret, compared via constant-time SHA-256 digest                                       | Provision narrowly scoped **read-only** credentials; issue/revoke fixed-purpose one-use _approval grants_                | Never sent to agent prompt or stored in DB. Changing/invalidating configuration clears all credentials and grants |
| `agent`                    | One 32-byte random bearer issued only after explicit operator authentication, hashed in process memory          | `READ_VERIFIED` for exactly its trusted repository/task/session/agent scope; **no approve/write/shell/Git/merge/Docker** | Maximum 15 minutes; revoke by credential ID; restart invalidates                                                  |
| `external` MCP client      | Separate, explicitly provisioned random bearer; `DEV_HUB_MEMORY_EXTERNAL_READ_ENABLE=true` required in addition | `READ_VERIFIED` only; never operator approval, never remote network access granted by token alone                        | Maximum 5 minutes; revocable; no external HTTP/MCP endpoint yet                                                   |
| One-time operator approval | Fresh 32-byte random grant token bound to `repository + action + recordId + expectedRevision + fingerprint`     | Only `APPROVE_MEMORY_PROPOSAL` or `REVOKE_MEMORY_RECORD`; **this PR performs no DB mutation**                            | 45 seconds, single use, grant-ID revocation, wrong-context attempt consumes token, restart/rotation revokes       |

Credential and grant maps contain **only SHA-256 token hashes**, never raw bearer values. A token is shown once as the direct result of an explicit trusted operator action; it must not be logged or sent to Codex. Audit snapshots are bounded to 256 metadata-only events: type, fixed operator actor ID, allowed repository, generated resource ID and timestamp, never secret, token, arbitrary chat body, Git SHA from an unverified source or raw prompts. No file-based token store; restarting Nest revokes everything. Bad operator-secret attempts are limited to 12 per minute **per local process**; an eventual multi-instance auth deployment will require distributed rate limits and persistent revocation before the feature can be enabled remotely.

Before an operator can issue a read-only agent credential over HTTP, `MemoryOperatorCredentialService` now checks the explicitly allowed repository, validates all requested UUID scopes, and performs a read-only PostgreSQL membership check using the dedicated Hub memory database. An unknown repository, agent, task, session or unrelated agent/task pairing is refused **before** token creation. A valid bearer requires independent database binding **on every list, detail and revision request**; issuing a token alone does not activate reads. No browser localStorage/cookie, MCP interface or agent prompt has access to the operator secret. A read-token alone can never create or approve a write grant.

## Error boundaries and review gates

`memory-http-identity.ts` provides the strict HTTP bearer helper used by all opt-in memory read endpoints which accepts only a strict `Authorization: Bearer <43-character-token>` header after local network/Origin/Host checks and translates errors to **401** (missing/invalid credentials), **403** (forbidden scope or origin), **429** (rate limit), **503** (disabled/unavailable). No errors include raw secrets. Without the additional read flag all memory GET routes stay 503; status stays 503 unconditionally. The helper does not grant authority merely because the process is bound to `127.0.0.1`.

Security acceptance tests in `apps/api/test/memory-authorization.spec.ts` and `memory-http-identity.spec.ts` cover secret separation, default deny, explicit allowlist, remote/CSRF/Origin/Host rejection, token-URL rejection, anonymous read, per-repo/task scope, external-client opt-in, wrong operator secret, expired/replayed/revoked grants, secret rotation, rate limits and audit confidentiality. `pnpm check` exercises these with **no PostgreSQL connection**. No migrations, credential persisted storage, model changes or CLI commands are introduced.

**Next gate:** review completed memory read identity acceptance criteria and threat-model checks, then advance to human-approved proposals/mutation in Issue #40. List, detail and verified revisions have real positive and negative Nest HTTP e2e tests, strict query validation and independent opt-in. Issue #40 then implements explicit human-reviewed approval and CAS/audit DB writes using the one-time grant interface after a separate review. Do not conflate an issued grant with approved/persisted memory; no provider or operation here can modify records. Rollback is disabling `DEV_HUB_MEMORY_SECURITY_ENABLE` (or deploying the prior version); no data migration or JSON changes required.
