# Shared Agent Memory read engine — implementation slice #38

**Status: explicitly opted-in HTTP verified list, detail and revision reads.** `GET /v1/memory?repository=owner/name` is now wired to a repository-scoped verified-only query behind an independently disabled-by-default `DEV_HUB_MEMORY_READ_HTTP_ENABLE=true` flag. It requires a valid local Bearer, a registered repository/agent/task/session binding in the dedicated Hub PostgreSQL, and all memory/security flags and secrets. Without this independent switch, the endpoint remains **503 Disabled** even with a valid bearer. The same opt-in and per-request bearer/DB binding gate protects `GET /v1/memory/:id?repository=owner/name` and `GET /v1/memory/:id/revisions?repository=owner/name`. `/v1/memory/status` remains **503**. Existing Workspace JSON, GitHub control plane and Gym Platform are unaffected. No write/mutation route, MCP, Codex injection or implicit privilege is introduced.

## Internal read contract

`packages/contracts/src/memory-read.ts` exports strict Zod v1 read query, trusted context, item/page and revisions DTOs. Only these explicit read-only route shapes are enabled when the separate read flag is set:

| Proposed path                                                    | Purpose after #39                                     | Current HTTP behavior                              |
| ---------------------------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------- |
| `GET /v1/memory?repository=&scope=&taskId=&kind=&limit=&cursor=` | Verified, sourced and unexpired list only             | 200 after explicit opt-in; otherwise 503           |
| `GET /v1/memory/:id?repository=owner/name`                       | Exact repository-scoped record, never cross-task      | 200 visible item / 404 invisible; otherwise 503    |
| `GET /v1/memory/:id/revisions?repository=owner/name`             | Visible, verified revision snapshots, bounded history | 200 visible history / 404 invisible; otherwise 503 |
| `GET /v1/memory/status`                                          | Disabled rollout state (existing #36 route)           | 503                                                |

`MemoryQueryService` accepts **two separate inputs**: a _trusted_ `MemoryReadContext` (repository, optional taskId/sessionId/agentId), and an _untrusted_ filter query (repository, optional scope/taskId/kind, bounded limit/cursor). The repository and task requested by the filter must match the trusted context, otherwise the service returns a uniform not-found error. For real HTTP access, agent credentials must carry an exact registered `repository + agentId + taskId + sessionId` tuple, and the server revalidates that membership against PostgreSQL on every list/detail/revision request. Missing session/task rejects before DB; external/MCP bearers are never accepted on agent HTTP routes, even when their separate flag is on. **Never derive the trusted context from query parameters or localStorage.** Only the bearer-derived, independently reverified principal supplies it; untrusted query filters cannot elevate scope. List, detail and revision routes call the same read engine only **after** per-request bearer and registered repo/task/session/agent DB binding. Detail and revision requests accept only an explicit repository query and UUID record ID (no user-provided task/session/agent). Invalid identifiers/extra query params give 400; foreign repository, hidden/expired/unverified/unsourced or missing record gives the same 404. Each response is `Cache-Control: no-store`. See [security](security.md).

Default list includes only `VERIFIED` rows with `verifiedBy`, `verifiedAt` and a **same-repository provenance record**, unexpired as of the SQL read and no stale GitHub provenance beyond 60 seconds. Provenance includes actor/source reference, SHA and observation timestamp; it is **untrusted data** and must never be executed or treated as instructions. GitHub remains authoritative for current PR/CI facts; before any Git write, independently refresh the relevant SHA and CI state. Proposed/revoked/superseded/expired/unsourced records never enter default read responses. There is **no read cache**.

Project-scope rows are visible to authorized repository principals only when they are not agent-private; task-scope rows additionally require the exact authorized taskId; session-scope rows require exact sessionId. Agent-specific records also require an exact matching trusted agentId. Database tenant FKs from #37 remain in force but are not a substitute for query-level authorization.

## Keyset pagination and failure behavior

List defaults to 20 results and enforces 1–50 per page. Rows sort deterministically by `(updatedAt DESC, id DESC)`; cursors contain that key and a filter/context fingerprint, signed with HMAC-SHA256 using an injected, nonpersistent **32+ byte server-only signing key**. Reuse under another repository, context or filter and tampering are rejected before DB access. No cursor can grant additional repository/task/session/agent visibility. Pagination is stable for **unchanged records**; concurrent edits and expiries may change visibility, so do not claim a frozen snapshot. Cursor key rotation intentionally invalidates old cursors. A valid page provides `nextCursor` or `null`; HTTP status translation is active for the list: malformed queries or tampered cursors return **400**, cross-repository/task filters **404**, missing/invalid bearer **401**, forbidden Origin/Host/DB identity **403**, and disabled/failed database **503** without echoing SQL errors, sources or credentials.

`GET /:id/revisions?repository=owner/name` returns **at most 100 verified revisions** for a visible, verified, sourced record. This bounded result is not an archive/export API. Future authenticated operator history UI (#45) must handle full revision paging and must not disclose unapproved historical proposal text in default agent context.

`pnpm check` runs unit/contract tests with no database (integration specs are explicitly skipped). The opt-in `memory-postgres` GitHub workflow uses an isolated ephemeral `gym_dev_hub_memory_test`, applies the #36/#37 migrations, runs real SQL negative integration tests for two repositories, visibility, freshness, keyset ordering, tamper and cross-context cursors, then runs full `pnpm check`. Local production API smoke must return 503 for all reserved GET routes by default; only the explicit independent read opt-in with valid Bearer and real scoped DB membership allows 200 for list, authorized detail and bounded revision routes. `/v1/memory/status` stays 503. Health and Workspace remain 200.

**Rollout:** list, detail and revisions activation requires the same explicit, local-only third flag. Never remove Bearer authentication or database identity binding. The separate proposal-only `POST /v1/memory/proposals` flag allows only unverified `PROPOSED` record insertion; no status route, approval grant, existing-record mutation, external MCP or Codex injection is enabled. See [proposal intake](memory-proposals.md). #40 separately implements operator-reviewed proposals/CAS/audit; database failures return 503, not an empty list. Rollback: set `DEV_HUB_MEMORY_READ_HTTP_ENABLE=false`; no migration/DB schema changed, original JSON state remains intact.

## Issue #39 follow-up: bearer-to-database membership gate

The unmounted `authenticateMemoryHttpReadWithDatabase` helper first authenticates the local Bearer and then performs one parameterized, fail-closed PostgreSQL identity lookup via `verifyMemoryPrincipalBinding`. It verifies that the repository exists, task and agent IDs belong to that same repository, session IDs match the exact task/agent scope, and agent+task scope has a genuine linked session. Unknown members fail with 403; database errors fail with 503. No request query/header claiming a repository is trusted. The initial read-identity slice did not enable credential issuance; a later operator-only HTTP controller now issues and revokes **agent** read-only bearers after this DB binding succeeds. The separately flagged list, detail and verified revision routes are enabled when explicitly configured; a separately gated `PROPOSE_MEMORY` endpoint can insert only unverified `PROPOSED` records; a separately gated operator-only CAS approval route exists, but agent read/proposal Bearers cannot access it; reject/revoke/supersede and general record editing remain disabled.

Unit tests run without a database. A separate opt-in integration spec runs under the already-isolated `gym_dev_hub_memory_test` PostgreSQL CI job and covers positive, cross-repo, cross-task, cross-session and missing-identity cases. The operator-only local provisioning/revocation and independently flagged memory list/detail/revision GETs are now covered by real Nest HTTP request-level positive and negative e2e tests. The existing real PostgreSQL query integration suite validates inaccessible/expired/unverified records and verified-history visibility. Status remains 503.
